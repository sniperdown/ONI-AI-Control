## 0. 一页结论

1. **这不是"走了很多弯路"的项目，是"用 5 天把游戏内部一次性摸了一遍"的项目。** 产物质量高于大多数业余 mod；真正的浪费集中在**三类可预防的返工**上。
2. **钱不是问题。** 截图那个会话 11.66 亿 token ≈ **¥48**；11-14 ~ 11-18 全机记账 41.0 亿 token / **¥170**，余额口径 **¥220**。按 ¥0.041 / 百万 token 的混合单价，"烧掉多少 token"这个问题的答案是**一个会话 ~¥50**。
3. **贵的是轮次。** 缓存命中 99.7%、输入:输出 = **533 : 1**：每写 1 个 token 要重读 500 个 token 的历史。省钱杠杆已经用尽，能省的只有"上下文长度"和"轮次数量"。
4. **最该改的不是"少犯错"**，是让一次错误的发现成本，从"一天 12 个版本"降到"一次探针"。

## 2. 该保留的四件事（不是客套，是下一个人别拆掉的东西）

1. **"诚实 API"**：`null` ≠ `false`；`*Unavailable` 只表示"取不到"；`409 NOT_APPLIED` 区分"下发了"和"生效了"；`dryRun` 与真做共用同一段解析；写操作默认 `confirm`。
   理由写在代码里也写在 CHANGELOG 里：**假成功会导致调用方重复下发**，重复下发比失败更贵（0.93.9、0.92.4 都为此改过返回码）。
2. **单点化**：`CellRules`（能不能挖）、`Chunks`（块规则）、`JobMarks.Resolve`（dryRun/真做）、`UiQuery.PathOf`（path 生成）、`JsonCheck`（下发前护栏）。
   每一次"同一事实两处实现"都出过事：`area.mineable=144` vs `dig.marked=419`、`/v1/marks` 读成熟度而 `/v1/job` 读标记、两套 path 写法。
3. **可对数**：`scanned == count + filteredByFog + filteredInvalid + notEmittedDueToLimit`、`count == defsCount == buildings.length`、`cells.mineable + unmineable + alreadyDigMarked == solid`。**能用等式自证的，不要用"看起来对"自证。**
4. **验收留痕**：9 篇 `[验收记录]` 每篇都有版本号、dll 字节数、SHA256、实测数字。这是这个项目最值钱的习惯。

### 3.1 把"弯路"拆成两类才公平

- **探索成本（必须付）**：游戏内部没有文档，要摸清 `MultiToggle` 的点击顺序、`MopPlacer` 的生命周期、URP 下的相机……只能试。0.94.7 的"三条试法 → 一条通"那张表，就是**探索的标准姿势**：先列候选、逐条真机否证、只把结论写进代码。
- **返工成本（可以不付）**：A、D、E 几乎全是返工；B 和 C 是"探索拖成了返工"——本来一次探针能结束的事，被写成了"改实现 → 装机 → 发现不对 → 再改实现"。

## 4. 可改进（按杠杆排）

### 4.1 指挥方式

1. **把"不能重启游戏"和"不能验证"分开说。** A 的直接原因是"按指示不装"，但指令的本意是"别打断我在玩的大档"。可以解耦：给一个 10 分钟小档窗口；或者说清"这版我只接受纯编译结论，一律记成债"，并让债在**下一轮被消费掉**，而不是攒成 15 条。
2. **验收条件写进需求，别让 AI 自拟判据。** 0.95.0 的 `blockingDialog` 是 AI 自己定的判据（"是 `KModalScreen` 就算"），它自己都在文档里写了会误报。一句"那研究面板会不会被报？"就能省掉一版。**"这一版如果错了，我会在游戏里看到什么"**比任何 review 都便宜。
3. **批次切到"可独立验收的单元"。** 5 天 66 版说明粒度已经很小，但同一版里塞了多个不相干特性（0.95.0 四件、0.92.0 五件），返工就按特性传染。一个特性一个版本，错了只回滚一个。
4. **事实只能有一个写入口。** 子会话写码、根会话装机实测的分工是对的，但两边都往同一份 CHANGELOG 写"验证到哪一步"，于是"至今未装机"和"实机证据"并存。规则：子会话写 `CHANGELOG.d/<版本>.md`（只写"我这边有没有运行期数据"），根会话合并；验证状态只进 `VERIFIED.md`。

### 4.2 成本

5. **长会话别背大文档。** 41 亿 token 里绝大部分是重复上下文；根会话还要反复读写 2,278 行 CHANGELOG + 206 KB API.md。`AI-GUIDE.md` 就是"给无上下文 AI 的两页纸"，**但它最后一天才出现**——应该第 2 天就有，之后每轮只读它 + 让子会话读细节。
6. **感知"轮次"而不是"token"。** 省钱的手段（缓存）已经用尽；剩下的杠杆是"少轮次、每轮更准"。一次探针 = 一轮；一次盲写 + 一次返工 = 四轮。

### 4.3 范围

7. **控制广度，转向使用。** 34 个端点里真正被调用过的估计不到一半（`/v1/tools`、`/v1/ui/widgets`、debug 类大概没人用）。而且**所有验收都是端点级的，没有一次任务级**——没有任何证据表明"一个 AI 拿这套 API 真能独立玩一局"。下一步的里程碑不该是第 35 个端点。

配套的流程改动（从本文件生效，不用工具）：

1. **判据先行**：写操作类需求，先答"游戏里怎么看出它发生了"；答不上来先做探针（探针用完即删，见 0.94.7 的做法）。
2. **CHANGELOG 只写"为什么"**，"验证到哪一步"从下一版起写进 `VERIFIED.md`——不要两处各写一份。
3. **发版前跑 `tools/smoke.ps1`**；它红了的版本不装。

## 6. 下一步：任务级验收（真正的里程碑）

现在的完成度是**端点级**的。建议下一轮的验收改成一句话的任务，让一个**没有上下文的 AI** 只拿 `AI-GUIDE.md` 完成：

> 在小档（Cycle 5 那个 1.3 MB 的「第七次重启」）上：读状态 → 挖 10 格 → 建一台电解器 → 搬 5 吨砂岩进箱子 → 截一张图证明。全程不许用桌面工具。

通过判据：

- 每一步只用 `/v1/*`，且**至少一次**是"AI 自己从 `/v1/ui` 里找到按钮并点了它"；
- 挖/建的证据是 `/v1/buildings`、`/v1/marks` 的回读，不是响应里的 `ok:true`；
- 中途失败能**自己恢复**（例如先 `dryRun` 发现目标不对，改坐标重试），而不是卡住；
- 全程给一份"我做了什么/我看到什么"的日志，人能从日志复现。

这一条过了，"AI 能玩缺氧"才算成立；过不了，缺的通常不是端点，是 `AI-GUIDE` 的信息密度和错误恢复路径。
