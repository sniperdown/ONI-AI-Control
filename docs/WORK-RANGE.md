# 作业范围与派单规矩（实测，2026-11-21）

来源：会话 lead，档「首都」cycle 6~8，mod `0.113.0`（`/v1/reach` 主判据已换成 `Navigator.CanReach`）。
全部数据都是**逐秒采样位置 + 同步看方块/元素变化**得出的，排除了"小人挪了位置才够到"的干扰。

## 一、作业范围（干活能到几格）

以**小人所在格**为原点，`dx` 水平、`dy` 垂直（`+y` 向上）：

| 方向 | 上限 | 证据 |
|---|---|---|
| 水平 | `|dx| ≤ 2` | `dx=±3` 的拆解标记全部保留、无人处理 |
| 垂直 | `−2 ≤ dy ≤ +3`（共 6 格高） | 平地站位 `(115,219)` 原地连挖 `(113,217..222)`：`dy=−2..+3` 全部完成；`dy=+4` 起（`(113,223)` 及以上）全部滞留 |

⇒ 范围是 **5 格宽 × 6 格高** 的矩形，**不是方形**，也不对称（向上 3、向下 2）。

### 重要修正（同日第二轮实测）：这个矩形是"每个站位"的，不是"小人当前位置"的

小人**会为了够到更远的格而沿梯子/走道换站位**。实测（`x=114` 梯子列，起点 `(114,219)`）：

```
t2  (114,219) 挖掉 (112,218)   dy=-1
t7  (114,219) 挖掉 (112,217)   dy=-2
t13 (114,220) 挖掉 (112,223)   dy=+3   ← 先挪到 220
t18 (114,220) 挖掉 (113,223)   dy=+3
t23 (114,221) 挖掉 (113,224)   dy=+3   ← 再挪到 221
t29 (114,223) 挖掉 (113,225)   dy=+2   ← 再挪到 223
t34 (114,223) 挖掉 (113,226)   dy=+3
```

9 个标记**全部完成，一个不剩**。第一次统计时我从"起点 `(114,219)`"去算 `(113,226)` 的偏移
（`dy=+7`）得出"超范围"，是错的 —— **它当时已经挪到 `(114,223)` 了**。

⇒ 正确判据：

```
目标会被干 ⟺ ∃ 可达站位 p : |目标.x−p.x| ≤ 2 ∧ −2 ≤ 目标.y−p.y ≤ +3
                  ∧ 目标有可站邻格（见下）
```

也就是要拿 `/v1/reach` 的**可达格集合**逐个套矩形，而不是只套小人当前那一格。

**另外这仍是"必要"条件，不是"充分"条件。** 还要满足：

> **目标必须有至少一个"小人能站到"的相邻格。**

反例（实测）：`(122,211)`、`(122,212)` 带拆解标记却无人处理，因为正下方的 `(122,213)` 是砖，
小人没有可站的邻格；把那格砖清掉后，两格立刻被拆。

**梯子/消防杆不改变水平上限，但站位本身仍算合格站位**：小人站在梯子格 `(114,219)` 上时，
照样挖到了 `dx=−2` 的 `(112,219..222)`。

## 二、派单方式：成批 > 逐个

实测两组对照：

- **一次只给 1 单**：小人下去干完 → `MoveToSafety` 回撤 → 再接下一单 → 再下去。看起来就是"反复上下抖动"。
- **一次给 5 单**（同排 `y=210` 的 `(120..124,210)`）：小人只下移一格站定，**原地连拆 5 格**（t6/t10/t13/t17/t21 各一格），干完才 `MoveToSafety`。

⇒ **AI 应该成批下标记**（一片该干的活一次挂上），而不是一个一个下。

## 三、三种"标记在、进度不动"的真实原因（别当成路径 bug）

| 现象 | 真实原因 | 证据 |
|---|---|---|
| 小人 `IdleChore`，标记仍在 | **目标没有可站立的相邻格**（被围住/正下方是自己要挖的格） | `(122,211/212)` 案例 |
| 小人 `IdleChore`，标记仍在 | **超出上面的矩形**（`|dx|>2` 或 `dy>+3` / `dy<−2`） | `(113,223)` 起、`dx=±3` 那批 |
| 小人 `BionicBedtimeMode` / 吃饭 | **需求抢占**（仿生人 3 天一睡，普通小人每天睡） | 吉滋镆挖到第 4 格去睡，进度停在 3 |

**并不是每个"停滞"都是坏消息**：仿生人睡完会自己回来接着干（用户跳过睡眠后它继续挖了）。

## 四、`/v1/move` 不能用来"钉住"小人

`POST /v1/move` 报 `canReach=true, moved=true, via=GoTo/2params`，但小人到位后立刻被
`MoveToSafety` 拉走（梯子格尤其明显）。**别用 move 做"把小人摆到某格"的实验前置条件**，
要么等它自己为了干活站过去，要么让玩家手动摆。

## 五、待办（尚未落到代码）

`/v1/job` 的 `build` / `dig` / `deconstruct` 响应还没有 `workRange` 块。建议加：

```json
"workRange": {
  "dx": -2, "dy": 3,
  "withinRect": true,              // |dx|<=2 && -2<=dy<=3
  "standableNeighbors": ["121,211"],
  "willEverDo": true,
  "reason": "ok"                   // 或 out_of_rect / no_standable_neighbor
}
```

理由：现在接口对"够不着"的标记只回 `ok` + `marked=true`，AI 会以为安排好了，
而标记会被**永久搁置且不会消失**（也没有 cancel 接口清掉它）。
